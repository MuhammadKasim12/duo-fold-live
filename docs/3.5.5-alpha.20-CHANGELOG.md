# 3.5.5-alpha.20 — Reuse the prepared live renderer across handoff

## Change
- Closing prewarm experiment: after a fully-open episode, enter CONCURRENT_INNER_DEFAULT within 12 degrees above the user's closing handoff threshold. The inner panel remains primary while the cover can power on early. The actual cover-primary request still uses the existing closing threshold. Preparation expires after 1500 ms if unused, releases on lock/stale input/mode change, and does not repeatedly rearm while paused. Fast folds that skip the preparation band switch normally.
- Live Windowed Glass keeps the D0 overlay composition and compiled renderer across both opening and closing remaps. Previously only closing could retain it; opening rebuilt the host after the display was already ON.
- Track physical panel identity as well as mode dimensions on the live primary host. Transitional OFF snapshots do not trigger live host recreation.
- Invalidate the old capture and request fresh destination content on adaptation. Existing capture dimension/age checks and committed-frame readiness remain in place.
- Observe display callbacks on a small dedicated handler thread and coalesce bursts into a main-thread update. Record callback receipt, main queue delay and update duration when a remap is handled. Configuration callbacks update directly instead of adding another main-loop turn.
- No changes to the handoff angle, artificial fade smoothing, gradualness, reveal duration, readiness gates, or screenshot handoff controller.

## Prewarming investigation
The opening preview already has the inner panel ON before the primary remap. Reusing the existing D0 host keeps our composition and shader prepared for either destination rather than constructing them after switching. This is app-side preparation, not a claim that native activation is faster.

AOSP LogicalDisplayMapper can wait for transitioning displays to turn OFF before applying a new layout. This is consistent with the reported brief OFF interval even with both panels initially ON. AOSP is explanatory evidence, not proof of Samsung's proprietary implementation:
https://android.googlesource.com/platform/frameworks/base/+/main/services/core/java/com/android/server/display/LogicalDisplayMapper.java

For closing, the supported concurrent-inner state is used as a bounded preparation request; this can turn on the secondary cover without deliberately changing the primary mapping. Its physical timing benefit remains unmeasured.

No documented Samsung per-panel prepare-only command was verified. The device exposes setEarlyWakeUp(boolean), but its firmware-specific semantics, scope and cleanup contract remain unverified. No speculative power call is introduced. Alpha.12's accepted ON overrides did not eliminate the observed OFF interval.

## Device validation needed
Use Live Screen / Windowed Glass, both directions, with the same fade settings and a fullscreen app. Compare request-to-D0-ON timings separately from callback queue, retained-host update, and fresh glass commit timings. Check rotations, reversing near the handoff, locking/unlocking, and absence of wrong-panel frames. Software commits do not establish optical visibility. Retaining the window context across opening is experimental and needs device verification.
